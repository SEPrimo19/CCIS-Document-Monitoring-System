### Defect found in the TEST SCRIPT (not the application) — fixed, not an app bug

- **What**: `suite_faculty_flow.sh` (and identically `suite_resubmit.sh`) asserted the re-upload

- **Root cause**: test-script regex too narrow for HTML-entity-encoded apostrophes; not an app
  defect. **Fixed** by broadening the match to the entity-independent substring
  `"be uploaded to right now"` in both `suite_faculty_flow.sh:68` and `suite_resubmit.sh:56`.
  Re-ran after the fix: passes, and the underlying enforcement (version does not advance, status
  guard rejects) was already correct before the fix — only the test assertion was wrong.

### Observation (not a confirmed defect — noted for completeness per the "distinguish test-could-not-be-run from defect-found" instruction)

While constructing the overdue-reminder fixture, an interesting property of the dedup logic
surfaced: `generateOverdueReminders()`'s dedup guard (and identically
`generateDeadlineReminders()`'s) keys ONLY on `(submission_id, user_id, type='pending', day)` —
it does not distinguish notifications by their actual purpose/title, and `type='pending'` is
shared between two different messages: `Notification::createRequirementAssigned()`'s
"New requirement to submit" and `generateOverdueReminders()`'s own "Requirement overdue". If
BOTH ever landed for the same submission on the same calendar day, the second would be silently
swallowed by the LEFT JOIN dedup, believing a same-day 'pending' notification was already sent.

**This is NOT reachable through the real application**: `RequirementController::validate()`
rejects a deadline earlier than today at publish time (verified by source read,
`app/Controllers/RequirementController.php:216-218`), so a freshly-published requirement can
never be simultaneously "just assigned today" and "already overdue today"; and
`Submission::backfillForFaculty()` (the other path that can create a new Pending submission
against an already-overdue requirement, for a newly-added faculty account) does NOT create a
competing "New requirement to submit" notification at all, so no collision arises there either.
I could only construct the colliding state by backdating a requirement's deadline directly via
SQL — something no user-facing flow can do. Reporting this as a low-severity design note for
the developers (the dedup key could be widened to include the notification's semantic reminder
kind, e.g. a `title` or a discriminating sub-type, to be robust against any FUTURE code path that
might create two different 'pending'-type notifications for the same submission on the same
day), not as a defect — I could not reproduce it through any real user action, so I am not
scoring it as a test failure.

### Coverage gap (honestly reported, not tested)

The "preserve the last active Secretary" guard (`User::deactivateGuardingLastAdmin` /
`updateProfileGuardingLastAdmin`, `app/Models/User.php`, invoked from `UserController.php`) is,
by its own doc comment, specifically a defense against a **race condition** between two
concurrent requests (a TOCTOU-safe atomic guard). Working through the logic: to even reach the
`toggleActive()`/`update()` code path, the ACTING user must themselves be an authenticated,
ACTIVE Secretary (`Guard::requireRole('Secretary')`). That means, in any single sequential
request, if the target account is the sole remaining active Secretary, the target and the actor
must be the same account — which the separate, unconditional self-lockout check catches FIRST,
before the last-admin guard is ever reached. So this guard's non-self branch is provably
unreachable via a single sequential request; it can only matter when two different Secretary
sessions race each other. I did not attempt to construct that race: the dev server used for this
whole run is PHP's built-in single-threaded server (`php -S`), which serves one request at a
time, so firing two "simultaneous" curl requests would not actually produce genuine concurrency
here — a test built for that would not be exercising the real race the guard defends against, and
would either trivially pass or trivially fail without saying anything about the guard's
correctness. I am reporting this as **untested**, not passing or failing it: it needs a
multi-worker/threaded server (or a direct unit/integration test against `User::deactivateGuardingLastAdmin`
that forces overlapping transactions) to verify for real.
